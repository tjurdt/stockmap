## 與本問題相關的資料流

1. `snapshot.py::build_stock_row`：以 `ClosingPrice` 與 `Change` 算 `chgPct = Change / (ClosingPrice - Change) * 100`。
2. `worker/src/index.ts::yahooQuote`：Yahoo `regularMarketPrice` 作現價，優先取 `chartPreviousClose` 作昨收；請求固定 `interval=1d&range=1d`。
3. `useLiveQuotes`：盤中每 20 秒、盤後每 10 分鐘抓報價。
4. `useLiveMarket` / `liveRow.ts`：若報價最新日期晚於歷史末列，補暫定日，估算價格、估值、動能。
5. `useLiveSnapshot` / `overlay.ts`：將報價覆蓋到快照，供散佈圖、報價清單、排行榜、個股頁共用。
6. 操作計畫、回測與自訂指標也會使用暫定歷史；操作計畫另透過 `priceOf` 優先使用報價。

## 已確認的問題

### 1. 新價格可能搭配舊漲跌幅

位置：`web/src/lib/overlay.ts:25`、`web/src/lib/overlay.test.ts:45`。

`prevClose` 缺漏或不大於零時，程式保留快照 `s.chgPct`，但仍覆蓋 `close`。
直接執行現有 `applyLive` 可重現：快照價格 100、漲幅 1%；收到新交易日價格 110、`prevClose=null`，輸出價格 110、漲幅仍為 1%。
舊漲幅沒有足夠依據可代表新交易日；也不能在未核對交易日與除權息參考價前，一律把快照收盤當昨收。

影響：散佈圖左側清單、散點顏色與 tooltip、漲跌幅軸、排行榜、個股因子。
現有測試明確要求這個 fallback，所以測試通過不能排除問題。

### 2. 舊報價可覆蓋較新的正式收盤

位置：`web/src/lib/overlay.ts:12`、`web/src/hooks/useLiveSnapshot.ts:26`。

`applyLive` 沒有收到 snapshot 日期，也不檢查個股報價日期。歷史補列拒絕舊日期，不代表報價覆蓋也會拒絕。
直接重現：快照價格 100，傳入較舊日期的價格 90、昨收 100，仍輸出價格 90、跌幅 -10%、市值同步降低。
同日盤中報價也可能覆蓋已入庫的正式收盤；目前無資料優先序可防止。

影響：與問題 1 相同；頁首還可能標示正式收盤日期，內容卻來自較舊報價。

### 3. 一批報價內的不同日期被合併成同一天

位置：`web/src/lib/liveRow.ts:51`、`:69`。

先取整批報價最大日期，但判斷每檔 `usable` 時只檢查價格，不檢查該檔日期。
直接重現：歷史最後一天 09-22；2330 報價日期 09-23、價格 110；2317 報價日期 09-21、價格 80。
結果新增 09-23 一列，2317 的 80 也被採用，而且 `quoted=2`。

影響：暫定價格、還原價、估值、動能、自訂指標、排名、回測及操作計畫。
過期報價應視為不可用；若依既有設計沿用舊收盤，也必須區分它不是當日成交。

### 4. 失敗或空回應後仍使用舊報價，操作計畫也沒有日期防護

位置：`web/src/hooks/useLiveQuotes.ts:47`、`web/src/hooks/useLiveMarket.ts:31`、`web/src/features/signal/report.ts:315`。

空回應只把 `failed` 設為 false，不清除既有 quotes；請求失敗則保留 quotes。
`isLive` 只檢查啟用與 Map 非空，不檢查有效日期。散佈圖與排行榜未呈現 `failed`。
`priceOf` 直接回傳 Map 內價格，操作計畫優先用它計算持股市值、損益與停損。

此項由控制流程確認，尚未做 React 輪詢時序測試。保留上次成功結果本身可以是設計選擇，但必須帶有過期狀態與使用限制。

## 其他相近風險

- 操作計畫 `report.ts:412` 的單日停損用前一列原始收盤；回測 `engine.ts:490`、`:746` 使用還原價報酬。在除權息時兩者可能產生不同判定。這是基準口徑問題，不能視為顯示百分比修正便已解決；尚未以真實除權息日驗證。
- `daily.py` 每次重寫快照，但 `prices.py:84` 與 `history.py:151` 略過同日資料。若來源同日修正收盤，快照可能更新、歷史與動能卻未更新。本次 09-22 資料沒有這個差異。
- `adjustments.py` 未以資料日期篩選除權息事件；每日 history 為 append-only，歷史還原價是否跨事件維持同一基準值得另案驗證。本次未認定既有歷史報酬錯誤。
- 散佈圖與排行榜在即時市值更新後仍直接 `slice(0, limit)`，沒有重排全池市值，因此「市值前 N 大」盤中可能仍是上次快照的集合。
- 專案文件已明列暫定資料的除權息誤差，以及落後多日只補最新一天的限制；單日停損、自訂 `chg(1)` 等使用相鄰列的邏輯也會受缺交易日影響。

## 已排查與證據限制

- 本機 09-22 的 60 檔 `chgPct` 與 `prices.json` 前一交易日原始收盤算出的百分比一致（檢查容許差 0.02 個百分點）。這是內部一致性檢查，不等於官方除權息參考價驗證。
- 60 檔快照的 close / mom20 / mom60 / mom121 與 history 當日末列完全一致。
- 從 2026 history 還原價重算、且序列足夠的 mom20 / mom60，與快照沒有超過 0.005 個百分點的差異。未在此檢查跨年度的 mom121。
- 09-23 約 10:00 台北時間，線上 Worker 的 2330 / 2317 / 2454 報價與昨收可正常配對。2330 為 2490 / 2460，計算 +1.2195%，Yahoo metadata 為 +1.22%。
- 約 10:03 對 60 代號的一次查詢實際回傳 50 筆，沒有缺昨收；當日回傳報價的昨收與本機 09-22 快照沒有差異。未把未回傳的 10 檔算成驗證成功；前端實際以 40 檔分批，此單次請求不完全等同 UI 請求。
- 線上 Worker 抽樣 `date=null`，而本機程式會填日期，顯示部署行為與本機存在差異。前端可由 ISO `time` 推日期，不能僅據此認定漲跌幅錯誤，也不能直接確定部署版本。
- 不足以認定 Yahoo `chartPreviousClose` 就是本次根因；這次抽樣值正常。
- 使用者尚未提供發生錯誤的代號、日期、實際及預期數字，因此已重現的是程式缺陷，尚未確認哪一項對應使用者當次畫面。

## 後續修正順序與驗收

1. 報價覆蓋傳入快照日期，逐檔檢查日期、有效價格，以及正式收盤與同日延遲報價的優先序。
2. 新交易日缺昨收時，不沿用舊日漲跌幅；沒有可信參考價則顯示缺值。若允許推算，需驗證交易日與來源口徑，不能只拿最新兩列相除。
3. 暫定列只採用屬於目標交易日的報價，`quoted` 計數與資料有效性保持一致。
4. 讓 `priceOf`、報價 freshness、失敗狀態與快照覆蓋共用相同有效性規則，避免操作計畫繼續採用被其他頁拒絕的報價。
5. 補上缺昨收、較舊日期、混合日期、同日正式收盤、盤後到隔日、空回應與失敗的回歸案例；修改目前要求保留舊漲幅的測試。
6. 除權息、同日來源修正、缺交易日與停損口徑另加資料案例驗證，再決定是否需修管線或重建歷史，不能手改產出 JSON。

待定位的實際事件：代號、交易日、頁面、顯示漲跌幅、預期漲跌幅。可先在同一時間比較「最新報價」開關前後；若價格相同但百分比改變，可進一步定位覆蓋來源。
